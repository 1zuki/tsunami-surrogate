\section{Training setup}
\label{sec:training}

\subsection{Data splits and normalization}
\label{subsec:train-splits}
All models are trained on the processed datasets described in Section~\ref{sec:data-generation}. As explained there, the training, validation, and test scenarios come from separately generated pools with separate fixed dataset seeds rather than from a random partition of the pool, which guarantees that no scenario is shared between them. The main experiment uses $10{,}000$ training scenarios, $1{,}000$ validation scenarios, and $2{,}500$ test scenarios per solver target, with the same scenario design reused across the hydrostatic, MUSCL-HR, and Boussinesq labels so the targets are directly comparable.

Normalization statistics are estimated on the training split only and then applied unchanged to the validation and test splits, so that no test information leaks into the feature scaling. Bathymetry and source input channels are standardized with training-split statistics. Trajectory targets are standardized for training and denormalized at evaluation time for the reported benchmark-scale metrics. The \texttt{initial\_depth} channel follows the shared preprocessing configuration and remains in stored scale for the reported runs.

\subsection{Optimization}
\label{subsec:train-optim}
All models are trained with the AdamW optimizer at an initial learning rate of $5 \times 10 ^ {-4}$ and a weight decay of $10 ^ {-6}$. The learning rate follows a cosine-annealing schedule that decays to a floor of $5 \times 10 ^ {-5}$ over the training budget, and the gradients are clipped to a maximum norm of $1.0$ for stability. Most direct models use a batch size of $64$; U-FNO uses $8$, and ConvLSTM uses $4$ because their architecture-specific activation footprints are larger.

Because the target is a $50$-frame trajectory, we train with a horizon-weighted mean-squared error that increases the weight of later frames,
\[
\mathcal{L} = \frac{\sum_{t = 1} ^ {T} w_t\, \mathrm{MSE}_t}{\sum_{t = 1} ^ {T} w_t},
\qquad
w_t = w_{\min} + (w_{\max} - w_{\min})\left(\tfrac{t - 1}{T - 1}\right) ^ {p},
\]
where $\mathrm{MSE}_t$ is the mean-squared error of frame $t$ and we use $w_{\min} = 0.8$, $w_{\max} = 2.0$, and $p = 1.7$. Without this weighting, the optimizer tends to fit the easy early frames and leave the later, lower-amplitude part of the rollout blurry, which is exactly the regime that matters for a forecast horizon. The relative $L_2$ error on the validation split is used both as the checkpoint-selection metric, keeping the best epoch, and as the early-stopping criterion with a patience of $20$ epochs. One detail worth stating: this selection metric is the relative $L_2$ computed on the \emph{normalized} validation targets, whereas the accuracy tables we report later are in denormalized benchmark-scale units after the normalization is reversed. Because standardization subtracts the channel mean, the normalized and denormalized relative $L_2$ have different denominators and are not the same number, so the best epoch is chosen on the normalized criterion and then scored on the denormalized metrics rather than being selected directly on the denormalized error. To keep the comparison fair, the same-protocol direct models share a common upper training budget: each model is allowed up to $256$ epochs, the largest budget used by any model, and the same optimizer, schedule, loss, and stopping rule are applied to all of them unless a model-specific configuration explicitly changes only the architecture. Early stopping then halts each model on its own, when its validation error stops improving, so a faster-converging baseline is not penalized and a slower model is not cut short. In practice the budget is an upper bound rather than a fixed number of epochs, and most models stop well before reaching it.

\subsection{Experiment configurations}
\label{subsec:train-configs}

Each model--target pair is defined by a single configuration. The primary configurations train the Fourier Neural Operator on the Hydrostatic, MUSCL-HR, and Boussinesq labels, and the hydrostatic comparison set additionally includes F-FNO, FNO-modes8, FNO-modes20, U-FNO, WNO, CNN, U-Net, and ConvLSTM models. The direct configurations share the same data contract, target horizon, optimizer family, horizon-weighted loss, checkpoint metric, and maximum epoch budget; U-FNO and ConvLSTM use architecture-specific batch sizes, and ConvLSTM follows a sequential prediction path. Boussinesq is included because it gives a weakly dispersive contrast on the same scenarios, not because it is treated as a validated truth model.

The windowed configurations use the same hydrostatic data but change the supervised task from a direct $50$-frame forecast to a $K = 5$ frame block forecast conditioned on recent surface-elevation frames. The reported Window-FNO-5 and Window-F-FNO-5 rollouts are first-target-frame-seeded diagnostics at evaluation time and scored on the remaining $49$ predicted target frames, so they are used as drift diagnostics and are not treated as like-for-like with the direct single-pass prediction problem.

For the uncertainty experiments we train a deep ensemble of seven members that differ only in their random seed, following the procedure of Section~\ref{subsec:uncertainty}. The ensemble shares the architecture and the training protocol of a single FNO model and only changes the seed, so any spread between members reflects optimization stochasticity rather than a different model design.

\subsection{Hardware and runtime setting}
\label{subsec:train-hardware}

Dataset generation was performed on a Google Cloud AMD EPYC 9B45 CPU host with numerical-library thread limits pinned per worker, because the numerical references are the main construction bottleneck. The final controlled inference and solver-speed benchmark was run on an Intel Core i5-13420H CPU and an NVIDIA GeForce RTX 4050 Laptop GPU. Training used available CUDA hardware across the campaign, but the early run metadata does not record a complete, consistent hardware allocation for every checkpoint, so we do not report a controlled cross-model training-time comparison.

The resulting runtime numbers should therefore be interpreted as measurements under a resource-conscious research setup rather than as optimized production benchmarks. They quantify acceleration relative to the vectorized NumPy/SciPy references used in this study, not relative to operational or GPU-accelerated tsunami codes. The ordinary direct and window models use seed $18$; the six subset-size scaling runs use seed $42$, while the separately plotted $10{,}000$-sample comparator is the seed-$18$ direct FNO; and the ensemble uses the fixed seeds $\{11, 22, 33, 44, 55, 66, 77\}$. Every reported training run retains its resolved configuration, a finite contiguous epoch history, and both the selected and final checkpoints. The direct architecture table remains a selected single-seed comparison; the seven additional seeds quantify stability and uncertainty for the Hydrostatic FNO only.
