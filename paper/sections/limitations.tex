\section{Limitations}
\label{sec:limitations}

The first limitation is that this is a controlled synthetic benchmark. Procedural bathymetry and source fields provide many wave-propagation cases, but they do not replace surveyed bathymetry, realistic earthquake rupture models, tides, bottom friction, coastal inundation geometry, or validation against observed tsunami records. The 10-crop real-bathymetry suite is fully wet and uses synthetic sources, so it tests morphology transfer outside the procedural terrain distribution, not readiness for operational tsunami warning or site-specific hazard assessment.

The labels are numerical reference solutions, not physical ground truth. The Hydrostatic and MUSCL-HR solvers are finite-volume shallow-water solvers with adaptive CFL time stepping, open boundaries, sponge damping, dry-cell protection, and quality checks for non-finite or unstable rollouts. These choices make the labels reproducible and safer for training, but they do not remove solver discretization error, boundary-treatment error, or resolution dependence. Therefore, an error number in this paper is an error against a stated solver and configuration, not against the real ocean. This is why we keep the raw solver-vs-solver gap separate from the surrogate-vs-surrogate error.

The Boussinesq comparison reference also has a limited interpretation. The implemented solver is an elevation-only weakly dispersive model with its own acceleration solve, filtering, sponge damping, finite-depth safeguards, and convergence checks rather than a full nonlinear production Boussinesq tsunami model. It is useful for comparison with Hydrostatic and MUSCL-HR on shared scenarios, but it should not be treated as real physical ground truth or as an automatic upgrade over the shallow-water labels.

The runtime and hardware comparisons are implementation-level comparisons. The solver timing scripts re-run the NumPy reference solvers on CPU from cached bathymetry/source scenarios, while the neural model can be timed on CPU or GPU with recorded batch size, precision, and TF32 settings. Dataset generation used an 8-core AMD EPYC 9B45 CPU server, while training and evaluation used an NVIDIA GeForce RTX 4050 Laptop GPU with an Intel Core i5-13420H CPU. This is the correct comparison for this repository and is representative of resource-constrained research environments, but it is not a universal speed claim against optimized production tsunami codes, GPU finite-volume solvers, adaptive-mesh solvers, or operational forecast systems. The speedup values should therefore be read as acceleration relative to our reproducible reference implementations, not as upper bounds on surrogate performance.

The OOD and resolution-transfer results depend on how the processed datasets are built. The OOD suite builder filters existing evaluation archives using metadata such as \texttt{source\_type}, \texttt{bathymetry\_type}, and \texttt{source\_strength}. This is useful for difficult-subgroup analysis, but the stricter held-out-family results show that removing a family before preprocessing can still produce large degradation, especially for rough sources. Similarly, proxy resolution transfer resizes processed inputs and targets, so it is a cheaper diagnostic and not the same as a newly simulated grid. Native-resolution evaluation is stronger, but only if the target normalization statistics are compatible with the training reference; otherwise a normalization mismatch can look like a resolution-generalization effect.

Finally, the paper is limited to forward emulation. The repository contains an inverse-dataset scaffold, including dense-map and sparse-gauge observation formats, but it does not yet train or validate an inverse model for source reconstruction or real-time data assimilation. Those problems need different inputs, metrics, uncertainty checks, and validation protocols, so we leave them for a separate follow-up study instead of mixing them into the forward-surrogate benchmark.
