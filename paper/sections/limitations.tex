\section{Limitations}
\label{sec:limitations}

The first limitation is that this is still a controlled synthetic benchmark. The bathymetry and source fields are generated procedurally, so they can give many different wave-propagation cases, but they do not replace surveyed bathymetry, realistic earthquake rupture models, tides, bottom friction, coastal inundation geometry, or validation against observed tsunami records. The synthetic-to-real bathymetry experiments are included to test transfer outside the procedural terrain distribution, not to claim that the model is ready for operational tsunami warning or site-specific hazard assessment.

The labels should also be understood as numerical reference solutions, not as physical ground truth. In the code, the Hydrostatic and MUSCL-HR solvers are finite-volume shallow-water solvers with adaptive CFL times stepping, open boundaries, sponge damping, dry-cell protection, and quality checks for non-finite or unstable rollouts. These choices make the labels reproducible and safer for training, but they do not remove solver discretization error, boundary-treatment error, or resolution dependence. Therefore, an error number in this paper is an error against a stated solver and configuration. It is not an error against the real ocean. This is why we keep the raw solver-vs-solver gap separate from the surrogate-vs-surrogate error.

The Boussinesq comparison reference also has a limited interpretation. The implemented solver is an elevation-only weakly dispersive model. Even though the paper-facing run uses the same bathymetry and source scenarios as the shallow-water solvers, it still has its own acceleration solve, filtering, sponge damping, finite-depth safeguards, and convergence checks rather than a full nonlinear production Boussinesq tsunami model. This makes it a useful weakly dispersive baseline for comparison with Hydrostatic and MUSCL-HR, but it should not be treated as real physical ground truth or as an automatic upgrade over the shallow-water labels.

The runtime comparisons are implementation-level comparisons. The solver timing scripts re-run the NumPy reference solvers on CPU from cached bathymetry/source scenarios, while the neural model can be timed on CPU or GPU with recorded batch size, precision, and TF32 settings. This is the correct comparison for this repository, but it is not a universal speed claim against optimized production tsunami codes, GPU finite-volume solvers, adaptive-mesh solvers, or operational forecast system. Thee speedup values should therefore be read as acceleration relative to our reproducible reference implementations.

The hardware settings are also a limitation. Although dataset generation was performed on an 8-core AMD EPYC 9B45 CPU server, training and evaluation were conducted on a mid-range laptop GPU, an NVIDIA GeForce RTX 4050 Laptop GPU, with an Intel Core i5-13420H CPU. This choice makes the experiments more representative of resource-constrained research environments, but it also means that the reported training time and inference throughput are not the upper bounds on surrogate performance. Different results may be obtained with larger GPUs, optimized numerical solvers, mixed-precision settings, or distributed learning.

The OOD and resolution-transfer results depend on how the processed datasets are built. The OOD suite builder filters existing evaluation archives using metadata such as \texttt{source\_type}, \texttt{bathymetry\_type}, and \texttt{source\_strength}. This is useful for difficult-subgroup analysis, but it is only a true held-out-family test when that family was removed from the training data before preprocessing. Similarly, proxy resolution transfer is produced by resizing processed inputs and targets, so it is a cheaper diagnostic and not the same as a newly simulated grid. Native-resolution evaluation is stronger, but only if the target normalization statistics are compatible with the training reference; otherwise a normalization mismatch can look like a resolution-generalization effect.

Finally, the paper is limited to forward emulation. The repository contains an inverse-dataset scaffold, including dense-map and sparse-gauge observation formats, but it does not yet train or validate an inverse model for source reconstruction. It also does not do real-time data assimilation. Those problems need different inputs, metrics, uncertainty checks, and validation protocols, so we leave them for a separate follow-up study instead of mixing them into the forward-surrogate benchmark.
